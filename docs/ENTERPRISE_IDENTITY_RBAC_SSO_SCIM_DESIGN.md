# تصميم هوية المؤسسات وإدارة الوصول في إنجاز

**الحالة:** RFC تأسيسي — محلّل الصلاحيات الأساسي منفذ في فرع المراجعة الحالي؛ الدعوات وSSO/SCIM غير مفعّلة.
**الغرض:** اعتماد نموذج هوية وصلاحيات يمكن توسيعه للشركات دون تجاوز عزل المساحات أو افتراض مزود هوية غير مختار.

## 1. ملخص القرار

الموجود اليوم هو مصادقة عبر Supabase Auth، وملف `users` مرتبط بمعرّف Auth، وعضوية `workspace_members` بأدوار `manager/member/viewer`. واجهات API تفرض عضوية مساحة العمل ثم تقيّد العمليات المعدّلة بدور المدير. لا توجد في مصدر المستودع واجهات دعوات أو إدارة عضوية أو إعداد SSO/SCIM.

**يُوصى بألا ننشئ دعوات تسجيل عادية أو نوصل SSO/SCIM قبل حسم نموذج الهوية للمؤسسة.** في المخطط الحالي، `users.auth_user_id` فريد، ولكل مستخدم `organization_id` واحد، كما أن نقطة `enjaz-auth-bridge` التي تنشئ الحسابات وتستعيد الجلسة غير موجودة كمصدر قابل للتعديل في هذا المستودع. قبول دعوة مستخدم جديد يتطلب ملفًا داخليًا وعضوية آمنة ومتوافقة مع تدفق التسجيل؛ إضافة جدول دعوات وحده ستنتج رابطًا لا يستطيع مستخدم جديد قبوله على نحو موثوق.

## 2. الوضع الحالي

- `authIdentity` يتحقق من bearer token مع Supabase Auth ثم يربطه بصف واحد عبر `users.auth_user_id`.
- `requireWorkspace` يطلب `workspaceId` ويتحقق من `workspace_members` قبل أي route محمية.
- الأدوار الحالية على مساحة العمل محصورة في `manager`, `member`, `viewer`.
- `requireManager` يفرض صلاحية المدير على إنشاء الموظف/المهمة والروتين والتكامل والموافقة.
- لا يوجد مسار لإرسال دعوة أو قبولها أو عرض أعضاء المساحة أو تعديل دورهم.
- تطبيق المصادقة يستدعي Edge Function باسم `enjaz-auth-bridge` مباشرة، لكن كود الوظيفة غير موجود ضمن شجرة المصدر التي تم فحصها.
- لا توجد إعدادات IdP أو endpoints SCIM 2.0 أو مخطط تخزين لها ضمن المستودع.

## 3. نموذج المؤسسة المقترح

### المسار الموصى به للشركات متعددة المؤسسات

فصل الهوية العالمية عن الانتماء المؤسسي:

1. `auth_identities`: سجل داخلي واحد لكل subject موثّق من مزود الهوية.
2. `organization_members`: علاقة عضو-مؤسسة، مع حالة وتاريخ دعوة ومصدر إدارة (`manual`, `sso`, `scim`).
3. `workspace_members`: علاقة عضو-مساحة مع دور/role assignment.
4. `identity_provider_connections`: موصل واحد أو أكثر للمؤسسة، مع بيانات مرجعية إلى مخزن أسرار لا بيانات سرية مكشوفة.
5. `directory_identities`: ربط `issuer + external_id` بمستخدم إنجاز مع تفرد مفهرس.

لا يُعاد استخدام `users.organization_id` كمرجع عالمي إذا كان الحساب قد ينتمي إلى مؤسستين؛ ذلك يخلق تعارضًا عند اختيار الملف في `/auth/me` ويجعل المؤسسة المشتقة غير واضحة. يجب توفير migration متدرج واختبار رجوع قبل تحويل المستخدمين الحاليين.

### المسار الأبسط إذا تقرر حصر الحساب بمؤسسة واحدة

يمكن الإبقاء على `users.auth_user_id` الفريد، لكن يجب أن تكون الدعوة إلى المؤسسة نفسها فقط، ويجب رفض أي دعوة لحساب مرتبط بمؤسسة أخرى برسالة واضحة. لا يجوز إنشاء profile ثانٍ لنفس Auth ID أو إعادة تعيين `organization_id` ضمن قبول الدعوة.

## 4. الدعوات — متطلبات MVP المقترحة

### دورة الدعوة

1. مدير مخول يرسل دعوة إلى بريد مطبّع lowercase ويختار دورًا من allowlist.
2. تنشأ دعوة ذات `token_hash` فقط (لا يُخزن الرمز الخام)، و`expires_at`، و`invited_by`، وحالة `pending`.
3. يُرسل الرابط عبر موفر بريد معتمد أو يُعرض كنسخة لمرة واحدة للمسؤول؛ لا يُسجّل الرمز في الخادم أو analytics.
4. المدعو يسجل/يدخل عبر تدفق Auth، ويتحقق الخادم من البريد المؤكد ومطابقته حرفيًا للبريد المدعو.
5. تنفذ عملية القبول بمعاملة واحدة: قفل الدعوة، التحقق من انتهاء الصلاحية/الإلغاء، إنشاء أو وصل الملف وفق نموذج المؤسسة، إضافة العضوية، تعليم الدعوة مقبولة، وإضافة حدث تدقيق.
6. إبطال الدعوة أو تدويرها آمن؛ القبول المكرر idempotent ولا يرفع الدور.

### بيانات الدعوة

`workspace_invitations(id, workspace_id, invited_email, role, token_hash, invited_by, expires_at, accepted_at, revoked_at, created_at)` مع قيد دور، وفهرس للطلبات المعلقة، وتفرد token hash، وRLS لا يسمح للمتصفح بقراءة الرمز أو إنشاء الدعوات مباشرة.

### ضوابط أساسية

- مدة صلاحية محدودة، حد معدل لمحاولات إنشاء/قبول الدعوات، ورمز عشوائي قوي أحادي الاستخدام.
- لا قبول عبر بريد غير مؤكد أو بريد غير مطابق، ولا cross-organization implicit join.
- لا تغيير للعضوية أو الدور من جهة العميل مباشرة.
- لا يجوز تخفيض/حذف آخر مدير في مساحة عمل.
- سجل تدقيق لكل إنشاء/إبطال/قبول/تغيير دور.
- توضيح ما إذا كان البريد يُرسل آليًا أم أن الرابط ينسخ يدويًا قبل الإطلاق.

## 5. نموذج الصلاحيات

### الأدوار المدمجة كبداية

| القدرة | Viewer | Member | Manager |
|---|---:|---:|---:|
| قراءة مساحة العمل والموظفين والمهام | نعم | نعم | نعم |
| إنشاء مهام وتشغيلها | لا | قرار منتج مطلوب | نعم |
| إنشاء/تعديل الموظفين والروتينات | لا | لا في النموذج الحالي | نعم |
| اتخاذ قرارات الموافقة | لا | قرار منتج مطلوب | نعم |
| إدارة الأعضاء والدعوات | لا | لا | نعم |
| إعداد SSO/SCIM والفوترة | لا | لا | مسؤول مؤسسة مخوّل فقط |

يستخدم API الآن `services/api/src/permissions.js` كمصفوفة مركزية ثابتة، وتستخدم المسارات أذونات مجال مسماة عبر `requirePermission(permission)`. ما تزال الكتابة محصورة بأدوار المدير/المسؤول/المالك؛ العضو والمشاهد للقراءة فقط إلى أن تُعتمد سياسة كتابة المهام. لا يوجد تخزين لأدوار مخصصة، وما يزال RLS بحاجة إلى تحقق تكاملي حقيقي.

### custom RBAC مستقبلًا

- سجل صلاحيات بأسماء ثابتة مثل `employees.read`, `employees.manage`, `automations.manage`, `approvals.decide`, `members.invite`, `billing.manage`, `sso.configure`.
- `workspace_roles` و`workspace_role_permissions` مع رفض افتراضي، ومنع منح صلاحيات غير موجودة.
- تحديد ما إذا كانت صلاحية المؤسسة تورّث إلى كل مساحات المؤسسة أو لا؛ الافتراضي الآمن هو عدم التوريث.
- اختبار deny-by-default وعزل workspace عبر API/RLS لكل صلاحية.

## 6. SSO للشركات

### بروتوكول الإعداد

- اختيار مزود/مزودي هوية رسميين ونمط Federation المطلوب (`OIDC` و/أو `SAML 2.0`) بعد التحقق من القدرات المتاحة في مزود المصادقة وخطة الحساب.
- تحقق من ملكية نطاق المؤسسة قبل ربطه؛ لا تُفرض SSO على نطاق مشترك أو غير موثق.
- ربط issuer/tenant و`subject` بمعرّف مستخدم داخلي ثابت، لا بالبريد وحده؛ البريد قد يتغير.
- خيارات تشغيل مستقلة: SSO اختياري، SSO إلزامي بعد فترة انتقال، حساب طوارئ break-glass محكوم ومراقب.
- منع open redirects، والتحقق من `state`, `nonce`, audience/issuer، وتوقيع assertions؛ الأسرار server-side فقط.
- سجل تدقيق لتغيير إعدادات الربط والدخول والفشل دون تسجيل assertion أو token.

## 7. SCIM 2.0

### endpoints المتوقعة

`/scim/v2/Users`, `/scim/v2/Users/{id}`, `/scim/v2/Groups`, `/scim/v2/Groups/{id}` مع دعم العمليات المطلوبة فعليًا من مزود المؤسسة فقط.

### متطلبات الأمان والتوافق

- bearer token مستقل لكل مؤسسة، يُخزن hash أو في خزنة أسرار، مع تدوير وإبطال ومهلة انتهاء؛ لا يظهر بعد الإنشاء.
- تحقّق من `externalId` فريد داخل `issuer/organization`، ودعم `filter`, `startIndex`, `count`, `schemas` وSCIM error shape وفق ما يتطلبه IdP المختار.
- تنفيذ `PATCH` idempotent، وتعامل آمن مع إعادة المحاولة وطلبات متزامنة.
- إيقاف مستخدم directory يزيل/يعطّل جلساته وعضوياته حسب سياسة معتمدة، لكنه لا يحذف السجلات المالية/التدقيقية ولا يسقط المهام القائمة بصمت.
- سجلات SCIM منفصلة مع وقت الطلب، الجهة، النتيجة وrequest ID؛ لا تسجل bearer tokens أو PII أكثر مما يلزم.
- دعم group-to-role mapping بallowlist؛ لا يقبل اسم مجموعة خارجيًا كصلاحية داخلية مباشرة.

## 8. الاعتماديات والقرارات المطلوبة قبل التنفيذ

1. اختيار نموذج الحساب: **مؤسسة واحدة لكل حساب** أم **حساب واحد ينتمي إلى مؤسسات متعددة** (الموصى به للشركات التي لديها مستشارون/شركات أم).
2. موفر الهوية الأول: Microsoft Entra ID أو Okta أو Google Workspace أو غيره، وبروتوكول federation المطلوب.
3. هل تريد SSO إلزاميًا أم اختياريًا؟ وهل تحتاج SCIM users فقط أم groups أيضًا؟
4. من يملك إدارة أعضاء المؤسسة: owner/admin منفصل عن manager لمساحة واحدة؟
5. موفر إرسال البريد للدعوات، أو اعتماد نسخ رابط دعوة لمرة واحدة في MVP.
6. توفير/إدخال مصدر `enjaz-auth-bridge` إلى المستودع أو اعتماد API موثق يضمن تدفق قبول الدعوة بعد تأكيد البريد.
7. توحيد مخطط profile قبل تمكين bootstrap أو دعوات مستخدم جديد: `onboarding-repository.js` يقرأ/يكتب `users.platform_role` ويستدعي `public.assign_first_platform_admin`. لا تعرّف أي من شجرتي API أو Supabase العمود/الدالة؛ مهاجرة Supabase الموجودة لا تفعل سوى `REVOKE` على الدالة، ما قد يفشل في تثبيت نظيف. أضف ترحيلًا متوافقًا وراجع سياسة تعيين أول platform admin قبل التفعيل.

### تحديث التنفيذ — 2026-10-18

- أُضيف في فرع المراجعة محلّل صلاحيات deny-by-default يغطي القراءة، الموظفين، الفرق، المهام، الأتمتة، الموافقات، التكاملات، الأعضاء، الفوترة، وإعدادات المؤسسة. المسارات الحالية تستخدم أذونات مجال صريحة مع استمرار السياسة القائمة للكتابة.
- يربط المخطط الحالي Auth ID واحدًا بملف Enjaz ذي `organization_id` واحد؛ يجب أن تكون دعوات الإصدار الأول داخل المؤسسة نفسها ما لم يُعتمد ترحيل متعدد المؤسسات.
- تظل واجهات الدعوات غير مفعّلة. غياب مصدر جسر المصادقة ونقص مهاجرة profile يمنعان إثبات إنشاء/قبول حساب جديد، وقد يعطلان bootstrap الحالي نفسه.
- توجد نقطتا كتابة خارج مصفوفة workspace عمدًا: `/api/v1/onboarding/bootstrap` يتطلب هوية Supabase موثقة قبل وجود عضوية، وفرع عامل الطابور في `/api/v1/runtime/process` يتطلب worker token؛ أما تشغيل المهمة يدويًا فيتطلب `workspace.manage`. اختبارات الحدود تحفظ هذه الاستثناءات ولا تمنحها أدوارًا للمستخدمين.

## 9. خطة التنفيذ الآمنة

- **المرحلة 0:** إصلاح profile/bootstrap migration source of truth، حسم نموذج الهوية، واستعادة مصدر/عقد auth bridge مع اختبارات تثبيت نظيف وترقية.
- **المرحلة 1:** إعادة هيكلة profile/organization membership بتوافق رجوعي وعزل RLS، مع سجلات تدقيق.
- **المرحلة 2:** دعوات email-matched أحادية الاستخدام + عرض/إبطال الدعوات + حماية آخر مدير.
- **المرحلة 3:** أُنجز الأساس: مصفوفة صلاحيات مركزية وواجهات API deny-by-default. لا تزال واجهة إدارة الأعضاء والأدوار الديناميكية ومواءمة RLS مطلوبة.
- **المرحلة 4:** تكامل SSO للمزود المختار في بيئة تجريبية، تحقق نطاق، break-glass، اختبار اختراق/رفض.
- **المرحلة 5:** SCIM 2.0 وmapping/deprovisioning بعد نجاح federation، ثم rollout تدريجي لكل مؤسسة.

لا يتم الإبلاغ عن دعوات أو SSO/SCIM كميزة جاهزة قبل نشر migration والـAPI ومصدر auth bridge، وإثبات تدفقات القبول/الرفض/إلغاء العضوية في قاعدة اختبار ومع مزود IdP حقيقي.
